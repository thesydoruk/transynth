## Multi-user mode

Типово інструмент працює в **single-user mode**:

- логін не потрібен;
- акаунтів немає;
- будь-хто, хто має доступ до URL, може робити все.

**Multi-user mode** вмикає:

- акаунти;
- логін;
- ролі;
- журнал активності.

Цей режим варто вмикати, якщо:

- один і той самий мод перекладає кілька людей;
- потрібен reviewer, який затверджує роботу перекладачів;
- потрібен аудит того, хто що змінював.

---

## Увімкнення multi-user mode

Додайте в `.env`:

```env
MULTI_USER=true
```

Після цього перезапустіть сервіс.

Що змінюється:

- з’являється **Login page** на `/login`;
- решта маршрутів редіректить на логін, поки користувач не автентифікується;
- під час першого запуску створюється bootstrap-акаунт **admin**;
- у навігації з’являється сторінка **Users** (`/users`) для адміністраторів;
- усі помітні дії починають атрибутуватися конкретному користувачеві в **Activity Log**;
- на API-рівні вмикається RBAC.

Повний список пов’язаних змінних дивіться в [Конфігурація](17-configuration.md).

## Ролі і дозволи

| Роль          | Що може робити                                                  |
| ------------- | --------------------------------------------------------------- |
| **Admin**     | Усе: імпорт, переклад, approve, експорт, керування користувачами, QA rules |
| **Translator**| Імпорт модів, переклад, запуск LLM, експорт                     |
| **Reviewer**  | Перегляд рядків, approve/reject перекладів, без імпорту й експорту |

Ролі задаються під час створення користувача й можуть бути змінені адміністратором у будь-який момент.

## Керування користувачами

Сторінка **Users** (`/users`) видима лише адміністраторам і лише тоді, коли ввімкнено multi-user mode.

Таблиця користувачів містить:

| Колонка         | Опис                                                      |
| ---------------- | --------------------------------------------------------- |
| **ID**           | Внутрішній числовий ідентифікатор                         |
| **Username**     | Логін для сторінки входу                                  |
| **Display Name** | Дружнє ім’я для Activity Log та атрибуції                 |
| **Role**         | Кольоровий бейдж ролі                                     |
| **Status**       | Active або Inactive                                       |
| **Created**      | Час створення акаунта                                     |
| **Actions**      | Адмінські дії                                             |

Дії адміністратора:

- **Toggle Active / Inactive** — деактивація без видалення;
- **Change Password** — зміна пароля будь-якого користувача.

Форма **Add User** містить поля:

- Username;
- Display Name;
- тимчасовий Password;
- Role.

Після натискання **Create User** користувач може увійти відразу.

Постійного видалення користувача зараз немає — замість цього слід деактивувати акаунт.

## Login і session

На сторінці **Login** (`/login`) потрібно ввести:

- **username**;
- **password**.

Поведінка сесій:

- сесії зберігаються в базі даних;
- типове життя сесії — **72 години**;
- браузер отримує HTTP-only cookie з `SameSite=Strict`;
- localStorage tokens не використовуються;
- опції `remember me` немає.

Щоб вийти, натисніть на своє ім’я у верхній навігації й оберіть **Log out**.
Сесію буде видалено на сервері, а cookie очищено.

Зміна пароля:

- кожен користувач може змінити власний пароль через сторінку Users;
- адміністратор може змінювати паролі будь-яких користувачів без знання поточного.

OAuth / SSO у поточній версії немає.

## Activity Log

Сторінка **Activity** (`/activity`) записує всі значущі події в системі:

- збереження перекладів;
- зміни статусів;
- імпорт модів;
- експорт;
- керування користувачами.

Є один основний фільтр:

| Фільтр         | Варіанти                                                                 |
| -------------- | ------------------------------------------------------------------------ |
| Action type    | `All`, `login`, `logout`, `translate`, `import`, `approve`, `export`, `create_user`, `update_user`, `change_password` |

Список пагінується по **50 записів на сторінку**.

Колонки:

| Колонка   | Опис                                                         |
| --------- | ------------------------------------------------------------ |
| **Time**  | Час дії                                                       |
| **User**  | Display name виконавця                                       |
| **Action**| Тип події                                                     |
| **Entity**| Зачеплена сутність, наприклад `user #5` чи `string #1042`    |
| **Details** | JSON-snippet з додатковим контекстом                       |

Додаткових фільтрів за датою, модом або користувачем у поточному UI немає.
Для вузького пошуку доводиться використовувати action filter або `Ctrl+F` у браузері.

## Review workflow для команди

Типовий командний процес виглядає так:

```text
Admin імпортує мод
   ↓
Translator перекладає (Draft / LLM Auto)
   ↓
Reviewer проходить Review Queue і approve / reset
   ↓
Translator виправляє повернені рядки
   ↓
Admin експортує фінальний реліз
```

Практична схема передачі роботи:

- перекладач повідомляє, що пакет `Auto`-рядків готовий до рев’ю;
- reviewer відкриває [Чергу рев’ю](15-review-queue.md) і проходить проблемні рядки;
- reviewer затверджує коректні та скидає неправильні;
- перекладач повертається до reset-рядків.

Автоматичних email-сповіщень у системі зараз немає, тому координація відбувається через ваш звичний чат або issue tracker.
