## Підтримувані типи файлів

| Файл                     | Опис                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| `.esp` / `.esm` / `.esl` | Плагін Bethesda-мода — основне джерело рядків для перекладу (FO4, FO76, FO3, FNV, OB, MW, SSE, SLE)  |
| `.zip` / `.7z` / `.rar`  | Архів мода, що містить плагін і, за потреби, відповідні `.ba2` / `.bsa`-файли або loose assets       |

## Початок імпорту

Відкрийте сторінку **Imports** за адресою `/imports`.

Поточний UI використовує **єдину сторінку імпортів**, а не три окремі вкладки.
Усі завантажені джоби відображаються в одному комбінованому списку з бейджем типу:

- `MOD` для імпорту плагінів або архівів
- `EET` для legacy project files
- `CSV` для CSV-імпортів

У верхній частині сторінки є одна спільна панель завантаження.
Користуйтеся нею так:

1. Відкрийте вибір файлів і виберіть один або кілька файлів.
2. Натисніть **Upload**.
3. Файл з’явиться у списку джоб, і імпорт стартує автоматично.
4. Кнопку play використовуйте для ручного перезапуску після паузи або помилки, або натисніть **Import All** для всіх pending-джобів.

Якщо сторінка ще порожня, поточний UI показує deterministic empty-state card із двома прямими next actions:

- **Choose files** — одразу відкриває вибір файлів
- **Browse NexusMods** — переводить у game-scoped браузер Nexus, щоб спочатку знайти мод для імпорту

У поточному вебінтерфейсі **немає окремої drag-and-drop зони**.
Користуйтеся звичайним file picker.

Вибір мови залежить від типу імпорту:

- **Імпорт мода, non-localized plugin:** стартує одразу з поточними/дефолтними мовами (`srcLang` і `tgtLang`) без modal-діалогу.
- **Імпорт мода, localized plugin:** імпортер читає доступні locale із STRINGS-файлів мода і теж стартує одразу.
- **EET import:** стартує одразу з поточними/дефолтними **Source Language** і **Target Language**.
- **CSV import:** стартує одразу з поточними/дефолтними **Source Language** і **Target Language**.

Практична примітка: якщо потрібно змінити мови перед повторним запуском paused/failed-джоба, скористайтеся діями джоба у списку.

## Прогрес імпорту (SSE)

Імпорт працює у фоні. Прогресбар оновлюється в реальному часі через
Server-Sent Events (SSE), без потреби оновлювати сторінку.

Коли ви стартуєте імпорт, браузер відкриває SSE-потік до backend.
Сторінка показує live percentage bar, поки worker надсилає `imported / total`.

Що видно в поточному UI:

- Бейдж статусу, поки джоб чекає, призупинений, впав або завершився.
- Live percentage bar, поки джоб реально виконується.
- Автоматичне оновлення списку джобів кожні кілька секунд, навіть без відкритого modal-вікна.

Поточний UI **не** показує багатокроковий список стадій на кшталт «Reading ESP», «Matching TM» або «Extracting PEX».
Замість цього прогрес відображається за кількістю записів.

Концептуально імпорт мода проходить через такі backend-етапи:

1. Завантаження і, для архівів, розпакування через 7-Zip.
2. Аналіз плагіна і побудова preview.
3. Інгест записів і source strings у базу даних.
4. За потреби — інгест MCM-текстів із `Interface/Translations`.
5. За потреби — інгест PEX-рядків із compiled Papyrus scripts.

EET і CSV імпорти простіші: вони парсять завантажений файл, інгестять записи і стрімлять числовий прогрес до завершення.

## Пауза та скасування

Для кожного запущеного джоба доступні такі дії:

- **Pause** (`⏸`) запитує cooperative stop.
- **Cancel** (`⏹`) запитує негайну зупинку.
- **Delete** (`🗑`) доступна лише тоді, коли джоб не виконується.

Що означає **Pause** у поточній реалізації:

- Worker завершує поточний batch, commit-ить уже оброблену роботу і позначає джоб як `paused`.
- Джоб лишається у списку.
- Лічильник `imported_records` зберігається.
- Натисніть **Start** ще раз, щоб продовжити з цього checkpoint.

Що означає **Cancel** у поточній реалізації:

- Worker зупиняється кооперативно на найближчому safe checkpoint.
- Уже commit-нуті записи лишаються в базі.
- Джоб **не** відкочується назад.
- Поточна реалізація ставить джобу статус `failed`, а не окремий `cancelled`.
- Оскільки лічильник прогресу зберігається, зазвичай можна знову натиснути **Start** і продовжити з останнього commit.

Що означає **Delete**:

- Для `MOD`-джобів UI запитує явне підтвердження перед видаленням.
- Видаляється рядок import job і завантажений вихідний файл.
- Для `MOD`-джобів, які були повноцінно імпортовані, також видаляється пов’язаний запис мода з бази (records/strings/translations видаляються каскадно).
- Якщо мод був завантажений з архіву, то за наявності також видаляється розпакована папка `_extracted_*`.

Тобто pause і cancel — це операційні команди, а не transactional rollback.

## Що відбувається під час імпорту

Коли ви імпортуєте мод, конвеєр:

1. Читає ESP/ESM/ESL binary і витягує всі translatable record fields.
2. За потреби читає пов’язаний BA2-архів для MCM-рядків і PEX-скриптів.
3. Зберігає кожен рядок із його FormID, типом запису (GRUP), ім’ям поля і EDID.
4. Запускає **TM waterfall**, щоб автоматично підставити переклади з попередньої роботи.

У поточному web importer workflow такий:

1. **Реєстрація завантаженого файла як import job.**
   Backend зберігає upload у `uploads/`, хешує файл і перевикористовує наявний job, якщо файл з таким самим хешем уже завантажувався.

2. **Для архівів — розпакування і пошук mod files.**
   `.zip`, `.7z` і `.rar` розпаковуються через 7-Zip. Імпортер шукає в дереві plugin-файли й BA2-архіви.

3. **Читання плагіна і preview translatable rows.**
   Імпортер парсить плагін через ESP reader і витягує translatable rows ще до повного ingest. Саме цей preview ви бачите в modal-вікні.

4. **Різна обробка localized і non-localized plugins.**
   Для localized plugin імпортер шукає відповідні `.strings`, `.dlstrings` і `.ilstrings` у sibling BA2 або loose `Strings/` directory. Для non-localized plugin він імпортує raw text прямо з плагіна і використовує мову, яку ви вибрали в modal-вікні.

5. **Записує records і strings у базу даних лише тоді, коли реально стартує імпорт мода.**
   Рядок у `mods` створюється ліниво вже під час самого імпорту, а не на етапі upload. Це не засмічує базу тимчасовими модами, які були потрібні лише для preview або одноразового перенесення перекладу. Коли імпорт стартує, кожен рядок пов’язується з модом, signature запису, path, editor ID, якщо він є, і normalised text, який потім використовують пошук та matching.

6. **За потреби — ingest тексту з BA2.**
   Після основного проходу по плагіну імпортер сканує BA2-файли або loose assets для:
   - **MCM text** у `Interface/Translations/*.txt`, що зберігається з signature `MCM`
   - **PEX strings** із compiled Papyrus scripts, що зберігаються з signature `PEX`

Важлива поправка: поточні web import workers **не** запускають Translation Memory waterfall автоматично під час імпорту.
TM application — це окрема дія, яку ви виконуєте пізніше в редакторі мода.

Терміни, які ви бачитимете у preview і таблицях редактора:

- **GRUP / Signature**: тип запису Bethesda, наприклад `NPC_`, `INFO`, `QUST`, `MCM` або `PEX`. Це показує, до якого об’єкта гри належить рядок.
- **FormID**: шістнадцятковий ідентифікатор запису всередині плагіна. Корисно для порівняння з xEdit чи іншими modding tools.
- **EDID**: editor ID, людиночитна внутрішня назва запису, якщо її визначив автор плагіна. Перекладачі часто використовують її як контекст для коротких або неоднозначних рядків.

## TM auto-match після імпорту

Після імпорту ви можете заповнити неперекладені рядки через Translation Memory.

Дивіться [Пам’ять перекладів](05-translation-memory.md), щоб зрозуміти, як працює точне/anchor TM-зіставлення.

Поточний web UI **не** застосовує TM автоматично як частину import worker.
Замість цього відкрийте імпортований мод у редакторі й використайте там **Apply TM**.

Чому це важливо:

- Імпорт створює inventory вихідних рядків.
- TM application — окремий явний крок.
- Diff/carry-over для новішої версії мода — теж окремий крок.

## Повторний імпорт оновленої версії мода

Якщо автор мода випускає нову версію, ви можете імпортувати її повторно.
Інструмент виявляє попередні версії того самого мода і пропонує shortcut до
workflow diff і carry-over.

Повний workflow дивіться у [Diff і повторний імпорт](11-diff-and-reimport.md).

У поточній реалізації це працює так:

1. Імпортуйте новіший plugin або archive.
2. Після завершення імпорту застосунок перевіряє, чи існують інші моди з тією ж назвою, але з іншим file hash.
3. Якщо старіші версії знайдено, з’являється **Reimport** modal.
4. Виберіть старішу версію і натисніть **Open Diff**.
5. Застосунок відкриє сторінку Diff із уже підставленими обома mod ID, щоб ви могли порівняти версії та свідомо перенести переклади.

Це не автоматичне копіювання.
Поточний UI лише виявляє зв’язок і допомагає перейти у diff workflow, але сам carry-over усе ще окрема дія.

Якщо ви завантажите точно той самий файл ще раз, backend перевикористає наявний import job за file hash і не створить дублікат.

## Застосування імпортованого мода-перекладу

У цьому розділі описано точну backend-логіку матчингу для сценаріїв застосування імпортованого перекладу.

Мета: взяти сирі рядки з імпортованого мода-перекладу (наприклад, RU) і
записати їх як переклади для цільового базового мода.

### Поточна поведінка apply-flow

- У режимі **Apply to existing** UI запитує лише мову перекладного мода і базовий мод.
- Цільова мова для запису визначається автоматично з мови імпортованого
  перекладного мода (окремого вибору target language більше немає).
- У звичайному тимчасовому apply-flow бекенд читає рядки напряму з import job на диску
  і **не** створює тимчасовий standalone mod row у `mods`.
- Завантажений файл після apply залишається на диску, щоб його можна було повторно
  використати або перевірити пізніше.
- Система не видаляє автоматично пов'язані import-артефакти з бази даних після apply.

### Чому strict FormID-only підхід ламається

Коли перекладний мод зроблено для старішої версії оригіналу, між версіями часто
змінюється структура:

- FormID може змінюватися.
- Path може відрізнятися деталями формату.
- Частина записів додається або видаляється.

Якщо матчити лише по `FormID + path`, значна частина валідних перекладів не знайдеться.

### Каскад зіставлення, який використовується в проєкті

Поточна реалізація використовує strict-to-loose каскад fallback-ключів.
Застосовується перший успішний **унікальний** збіг.

1. `identity`: `FormID + path` — точний структурний збіг.
2. `identity_ranked`: якщо одна й та сама пара `FormID + path` зустрічається кілька
   разів (типова ситуація для dialogue INFO-записів під одним топіком у Bethesda ESP),
   рядки порівнюються **позиційно**: n-й імпортований рядок відповідає n-му цільовому
   рядку в межах одного key-bucket. Для розрізнення записів із дублюючими ключами
   використовується внутрішній індекс.
3. `formid_signature_path`: `FormID + signature + path_simplified`
4. `edid_signature_path`: `EDID + signature + path_simplified`
5. `edid_path`: `EDID + path`
6. `edid_signature`: `EDID + signature`
7. `formid_signature`: `FormID + signature`
8. `formid_only`: `FormID`

Порядок підібраний так, щоб спочатку використовувати максимально надійні ключі,
а більш ризикові fallback-кроки запускати лише якщо строгі збіги не спрацювали.

### Захист від неоднозначних збігів

Для кожного типу ключа backend тримає map у режимі **лише унікальних** кандидатів:

- Якщо ключ відповідає одному тексту перекладу, він використовується.
- Якщо ключ відповідає різним текстам, ключ позначається неоднозначним і
  не застосовується автоматично.

Крок `identity_ranked` є єдиним винятком з цього правила: він розроблений
спеціально для ключів, які **за визначенням** є неоднозначними (кілька записів
з однаковим `FormID + path`). Замість відкидання такі записи вирівнюються за
`ROW_NUMBER()` у SQL-партиції — кожен екземпляр отримує стабільний слот.

Це зменшує ризик хибних автозаписів у слабших fallback-режимах,
особливо для `EDID`-матчингу.

### Нормалізація ключів перед порівнянням

Щоб стабілізувати матчинг між різними форматами шляху й регістром, backend нормалізує:

- `path`: lowercase, `\\` -> `/`, дублікати слешів згортаються.
- `FormID`: uppercased.
- `EDID`: lowercased.

Тому `INFO\\FULL` і `info/full` вважаються еквівалентними.

### Що навмисно пропускається

- Рядки цільового мода, які вже мають переклад у `targetLang`.
- Порожній імпортований текст.
- Неоднозначні fallback-ключі.
- Рядки без збігів (лише рахуються в статистиці).

### Спостережуваність у логах

Backend лог пише лічильники по кожному методу в полі `methods={...}`.
Це дозволяє побачити, де спрацював матчинг: на strict identity чи на fallback-кроках.

Приклад (форма):

```text
methods={"identity":6597,"identity_ranked":1524,"formid_signature_path":0,"edid_signature_path":0,"edid_path":0,"edid_signature":0,"formid_signature":0,"formid_only":0}
```

У наведеному прикладі 6597 рядків збіглися точно, а 1524 — вирівняно позиційно
через `identity_ranked` (дублюючі INFO-записи діалогів).

Якщо `identity` і `identity_ranked` обидва низькі, а fallback-лічильники високі, це зазвичай означає, що
перекладний мод базується на іншій версії або відмінній структурі записів.

## Імпорт BA2-архівів

BA2-архіви можуть містити:

- **MCM strings** — підписи опцій Mod Configuration Menu
- **PEX scripts** — рядкові літерали зі compiled Papyrus scripts

Поточний UI **не** приймає bare `.ba2` upload напряму.

Замість цього BA2-вміст знаходиться автоматично в таких випадках:

- Ви завантажуєте archive (`.zip`, `.7z`, `.rar`), який містить і plugin, і один або кілька BA2-файлів.
- Імпортований plugin обробляється з директорії, де вже лежать відповідні BA2 або loose assets.

Для звичайного браузерного сценарію найпрактичніше завантажувати повний архів, що містить plugin і пов’язані з ним asset-файли разом.

Як працює виявлення BA2:

- Для localized STRINGS data імпортер спочатку шукає BA2 з ім’ям на основі stem плагіна або `PluginName - Main.ba2`.
- Для MCM і PEX extraction імпортер сканує всі BA2-файли в директорії плагіна.
- Також підтримуються loose `Strings/`, `Interface/Translations/` і `Scripts/` там, де це доречно.

BA2 — опційний.
Імпорт лише ESP теж працює для non-localized plugins і для плагінів, де translatable text зберігається безпосередньо в записах плагіна.

Важливе обмеження: якщо ви завантажуєте archive з кількома plugins, поточний імпортер використовує перший знайдений plugin. Для повного контролю завантажуйте конкретний plugin або мінімальний archive лише з потрібними файлами.

## Вкладки зв'язків на сторінці мода Nexus

На маршруті Games (`/games/:gameId`) порожнє поле пошуку показує
пагінований повний список модів для вибраної гри.

Коли ви відкриваєте сторінку деталей мода з Games (`/games/:gameId/mods/:modId`),
нижній блок має три вкладки:

- **Можливі переклади** — евристичний список імовірних модів-перекладів,
  згрупованих за мовою з прапорами.
- **Потребує** — офіційний список залежностей Nexus, потрібних цьому моду.
- **Потрібен для** — офіційний список модів Nexus, які залежать від цього мода.

Кожен елемент має посилання на Nexus, якщо для зв'язаного мода є валідний
Nexus `modId`.
Якщо у Nexus GraphQL немає relation-даних для конкретного мода, вкладки
показують повідомлення про порожній список, а сторінка продовжує працювати.

У таблиці **Прикріплені файли** на сторінці мода кожен Nexus-файл також має
дві дії:

- **Скачати** — файл стрімиться через бекенд-проксі.
- **Імпортувати** — файл скачується на сервер і одразу запускається mod import
  job для вибраної гри.

## Імпорт EET-файлів (legacy)

EET-файли — це проєкти з legacy desktop-інструмента.
Імпорт EET-файла мігрує наявні переклади у pipeline database.

EET imports живуть на єдиній сторінці **Imports** як jobs з бейджем `EET`.

Workflow:

1. Завантажте `.eet`-файл.
2. Імпорт стартує автоматично з поточними/дефолтними мовами.
3. Відстежуйте прогрес у списку jobs.

Що імпортується з EET:

- Source strings
- Target translations, якщо вони є в записі EET
- EET status bytes

Мапінг статусів:

- `0x63` (`confirmed`) імпортується як human translation із повною впевненістю
- будь-який інший непорожній target text імпортується як automatic translation
- порожній target text створює лише source-string сторону

Порівняно з native mod import, EET import — це формат міграції, а не live-аналіз плагіна.
Він імпортує те, що є всередині EET-файла, і не аналізує BA2-архіви, loose STRINGS assets, MCM text files чи PEX scripts.

## Імпорт CSV-файлів

CSV-файли можуть містити попередньо перекладені рядки, експортовані з іншого інструмента.

CSV imports також відображаються на єдиній сторінці **Imports** як jobs із бейджем `CSV`.

Очікуваний формат у поточній реалізації:

- Кодування: UTF-8
- Роздільник: кома
- Котирування: стандартне CSV-котирування з подвоєнням подвійних лапок усередині quoted values
- Header-based mapping: порядок колонок не важливий, якщо потрібні назви заголовків присутні

Підтримувані колонки:

- `FormID`
- `Signature`
- `EDID`
- `Path`
- `Source`
- `Target`
- `Status`

Примітки про parser:

- Поточний parser — **comma-separated**, а не крапка з комою і не таб.
- Відсутні колонки допускаються, але імпорт найкорисніший, коли таблиця містить перелічені поля.
- Колонка `Path` сприймається як record field/path identifier для збереження та подальшого lookup.

Workflow preview:

1. Завантажте CSV-файл.
2. Імпорт стартує автоматично з поточними/дефолтними мовами.
3. Відстежуйте прогрес у списку jobs.

Обробка статусів:

- `confirmed` мапиться на human translation
- `untranslated` мапиться на untranslated status byte
- числові статуси приймаються як є
- будь-яке непорожнє `Target`, що не дорівнює `confirmed`, імпортується як automatic translation

Обробка конфліктів у поточному UI:

- Під час CSV-імпорту **немає interactive overwrite/merge dialog**.
- Імпортер інгестить рядки як вони були завантажені.
- Дублікати ідентичних перекладів для того самого імпортованого source string дедуплікуються constraint-ом у базі.
- Тому CSV-import найкраще підходить для початкового ingest або міграції, а не як інструмент точкового merge у вже відрев’юваний мод.

## Усунення проблем

- **"File too large"**
  Вебсервер обмежує multipart uploads змінною `UPLOAD_MAX_FILE_SIZE_MB` (за замовчуванням: `1024`, тобто 1 GiB). За потреби збільшіть значення в `.env` і перезапустіть backend. Також можна розбити завеликий архів або завантажити лише потрібний plugin.

- **"Unsupported format"**
  Поточні типи файлів, які приймає upload API: `.eet`, `.csv`, `.esp`, `.esm`, `.esl`, `.zip`, `.7z`, `.rar`. Bare `.ba2` API не приймає.

- **"No ESP/ESM/ESL plugin found in archive"**
  Ваш `.zip`, `.7z` або `.rar` не містив підтримуваного plugin. Розпакуйте його локально і перевірте, що archive справді містить потрібний плагін.

- **Імпорт localized mods падає, бо не знайдено locale files**
  Для localized plugins імпортер очікує відповідні STRINGS data в BA2 або loose `Strings/` folder. Якщо цих файлів немає, імпорт не зможе розв’язати LString text.

- **Імпорт ніби завис або SSE stream загубився**
  Оновіть сторінку і перевірте рядок job. Список оновлюється автоматично, тому running або completed job має з’явитися з актуальними лічильниками. Якщо job у статусі `paused` або `failed`, натисніть **Start**, щоб продовжити з останнього commit checkpoint.

- **Pause або Cancel не відкотили імпортовані рядки**
  Це очікувана поведінка поточної реалізації. Imports commit-яться пакетами і зберігають уже імпортовані records. Pause/cancel лише зупиняють майбутню роботу, але не rollback-ять базу.

- **Незрозуміла поведінка повторного upload**
  Backend дедуплікує за file hash. Якщо завантажити точно той самий файл ще раз, зазвичай повернеться вже існуючий job. Якщо завантажити інший файл із тією ж назвою мода, створиться ще одна версія мода, яку потім можна буде порівняти у diff workflow.

- **В archive кілька plugins**
  Поточний імпортер використовує перший знайдений plugin. Якщо вам потрібен конкретний, завантажте його напряму або зберіть менший archive лише з потрібними файлами.
