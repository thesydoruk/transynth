# 08 — Глосарій

Глосарій зберігає бажані переклади ключових термінів і підставляє їх у LLM-prompts, щоб термінологія залишалася узгодженою між усіма модами.

## Що таке глосарій?

Глосарій — це список термінологічних пар: **source term** і його бажаний **target translation**.

Приклад:

| Source term          | Translation      |
| -------------------- | ---------------- |
| Synth                | Синт             |
| Brotherhood of Steel | Братерство сталі |
| Vault                | Сховище          |
| Pip-Boy              | Піп-бой          |

Використання глосарію гарантує, що і перекладачі, і LLM-модель працюють з одними й тими самими термінами. Для великої локалізації це критично.

---

## Базовий глосарій Fallout 4 (сид)

Проєкт постачається з **готовим глосарієм** канонічної термінології Fallout 4 (`EN → UK`): фракції, локації, супутники, істоти, роботи, хемки, зброя/броня та атрибути S.P.E.C.I.A.L. Терміни відібрані з підтверджених перекладів базової гри (`Fallout4.esm`) за частотою вживання.

- **Джерело істини:** `src/resources/glossary/fo4-uk.ts` — куруваний, типізований список пар, що зберігається у git. Завдяки цьому термінологія не залежить лише від бази даних і ніколи не губиться.
- **Засів у базу:** виконайте

  ```bash
  npm run db:seed:glossary
  ```

  Скрипт **ідемпотентний** — повторні запуски лише оновлюють засіяні рядки (`source = 'seed:fo4-base'`) і **не чіпають** терміни, додані вручну через UI (`source = 'manual'`).

Щоб розширити базовий глосарій, додайте пари у `fo4-uk.ts` і знову запустіть команду засіву (рекомендований шлях для термінів, які мають жити в репозиторії), або додавайте разові терміни через сторінку **Glossary** у UI.

## Базовий глосарій Disco Elysium (сид)

Канон DE (`EN → UK`) лежить у `src/resources/glossary/disco-uk.ts`. Його
підставляють Disco-промпти перекладу й verify; `npm run db:seed:glossary` сіє
лише Fallout 4. Перед LLM і TTS зірчаста цензура lockit розгортається в повне
слово, тож пари на кшталт `faggot` / `Pissfaggot` можуть збігтися. Курсив
`*belong*` глосарій не чіпає.

## Відкриття сторінки Glossary

Відкрийте **Glossary** з картки **Terms** на хабі гри (`/glossary`). Вкладки Settings → Data немає. Список термінів спільний для мовної пари; у enforce-списку — моди поточної гри.

Сторінка відкривається з термінами для поточно вибраної мовної пари, типово `EN → UK`.

---

## Додавання термінів

Форма додавання знаходиться у верхній частині сторінки, під фільтрами мовної пари.

1. Виберіть **source language** і **target language**.
2. Введіть **source term** у ліве поле.
3. За бажанням введіть **translation** у праве поле.
4. Натисніть **Add Pair** або `Enter` із translation field.

Переклад можна тимчасово залишити порожнім — такий запис збережеться і в таблиці відображатиметься як `—`.

Обмеження:

- source term не може бути порожнім;
- дублікати `(term, src_lang, tgt_lang)` не дозволяються через унікальне обмеження в базі.

---

## Редагування і видалення термінів

Існуючі записи можна редагувати inline прямо в таблиці глосарію.

Щоб відредагувати пару термінів:

1. Натисніть **Редагувати** у відповідному рядку.
2. Оновіть source term і/або translation.
3. Натисніть **Зберегти** (або **Скасувати**, щоб відмінити зміни).

Щоб просто видалити термін, натисніть **✕** в останній колонці.
Видалення виконується відразу, без окремого confirm-dialog.

Видалення терміна:

- не змінює вже збережені переклади;
- лише припиняє майбутню підстановку цього терміна в LLM-prompts;
- також зупиняє генерацію `glossary_violation` для цього правила.

## Пошук у глосарії

Використовуйте пошуковий рядок над списком термінів, щоб фільтрувати записи за source, translation або обома полями.

Пошук виконується на сервері:

- при кожному введенні сторінка повторно запитує API;
- запит передається як параметр `q`;
- використовується case-insensitive substring match по колонках `term` і `translation`.

---

## Мовні пари

Глосарій підтримує кілька мовних пар.
Dropdown-и **Source lang** і **Target lang** визначають:

- які рядки показуються в таблиці;
- для якої мовної пари створюється новий термін.

Доступні варіанти: `EN`, `UK`, `All`.

Термін, створений для `EN → UK`, зберігається окремо від `EN → RU`.
Унікальний ключ у БД: `(term, src_lang, tgt_lang)`.

Якщо ви підтримуєте кілька мов призначення, для кожної з них потрібно створювати власний запис.

LLM translation route бере ту мовну пару, яка відповідає параметрам `srcLang` і `targetLang` конкретного запиту.

---

## Підстановка в LLM

Під час batch LLM translation pipeline для кожної порції (chunk) рядків:

1. Завантажується **весь** глосарій для відповідної мовної пари.
2. Відбираються лише **релевантні** терміни — ті, чий source-term реально трапляється в джерельних рядках цієї порції (збіг за межами слів `\b`). Це означає, що великий глосарій (сотні термінів) не обрізається за алфавітом, а в prompt потрапляє саме те, що потрібно для конкретних рядків.
3. Відібрані пари передаються в полі `glossary` JSON-запиту до моделі (обмеження — до 100 релевантних термінів на порцію, щоб контролювати розмір контексту).

Приклад вхідного запиту (фрагмент):

```json
{
  "target_language": "uk",
  "glossary": [
    { "term": "Brotherhood of Steel", "translation": "Братерство сталі" },
    { "term": "Power Armor", "translation": "Силова броня" }
  ],
  "items": [
    /* … рядки для перекладу … */
  ]
}
```

System prompt прямо вказує моделі, що поле `glossary` — **авторитетне** джерело і має пріоритет над типовими відповідниками. До підказки потрапляють лише ті терміни, у яких заповнена колонка `translation`; порожні записи ігноруються.

> **Примітка для розробників.** Раніше підставлялися перші 80 термінів _за алфавітом_ без прив'язки до батчу — релевантні терміни могли «не вміститися». Тепер фільтрація відбувається за вмістом порції (див. `relevantGlossaryForChunk` у `src/web/llm/translateBatch/glossary.ts`).

Окрім глосарію, ключові канонічні конвенції (напр. `...Rifle/Gun → ...карабін`, `caps → кришки`, `Vault → Сховище`) зашиті безпосередньо в український system prompt як орієнтир на випадок, коли термін відсутній у глосарії.

Модель усе ще може відхилятися від глосарію, особливо на коротких або неоднозначних термінах. Саме тому після AI-перекладу варто перевіряти рядки зі статусом `auto` і дивитися на `glossary_violation` у QA.

## Пакетна перевірка глосарію

Зазвичай порушення глосарію виявляються **при збереженні** — кожного разу, коли ви зберігаєте переклад, `refreshQAIssues` перевіряє його проти поточного глосарію. Але що робити, якщо ви додали нові терміни **після** того, як переклади вже були збережені?

Панель **Застосувати глосарій** внизу сторінки Glossary дозволяє повторно перевірити всі наявні переклади оптом.

### Як запустити

1. Перейдіть на **Glossary** у верхній навігації.
2. У панелі **Застосувати глосарій** (під формою додавання) оберіть конкретний мод або залиште **Усі моди**.
3. Натисніть **Запустити перевірку**.
4. Рушій видаляє всі попередні `glossary_violation` у зоні дії, потім перевіряє кожний перекладений рядок проти поточного глосарію.
5. З'являється результат: _«Перевірено N рядків — знайдено M порушень.»_

### Деталі

- **Межі слів** — пошук у source використовує `\b`-анкери, тому термін «iron» **не** збігатиметься всередині «environment» чи «ironed». Це запобігає хибним спрацюванням.
- **Без урахування регістру** — порівняння source і target ігнорують регістр.
- Перевірка target використовує простий substring match (без меж слів), оскільки кирилиця має відмінювання.
- Операція виконується всередині однієї транзакції БД, тому або всі зміни фіксуються, або жодні.
- Після перевірки перейдіть до будь-якого mod editor і перегляньте вкладку **QA** для нових `glossary_violation`.

### API endpoint

```
POST /api/glossary/enforce
Body (JSON, усі поля необов'язкові):
  { "modId": 42, "targetLang": "uk" }
Відповідь:
  { "checked": 1234, "violations": 17 }
```

## Рекомендована практика

- Додавайте терміни **до** запуску LLM-перекладу.
- Найперше заносьте proper nouns: фракції, локації, назви предметів, імена NPC, специфічні ігрові поняття.
- Зберігайте однакову капіталізацію, близьку до внутрішньоігрової.
- Для одного терміна використовуйте один канонічний переклад, не створюючи конкуруючих варіантів.
- Після batch-перекладу переглядайте `auto`-рядки з QA-попередженнями `glossary_violation`.
- Терміни, які мають бути спільними для команди й переживати скидання БД, додавайте у `src/resources/glossary/fo4-uk.ts` і застосовуйте через `npm run db:seed:glossary` — так глосарій зберігається в git. Разові/локальні терміни зручніше додавати через UI.
